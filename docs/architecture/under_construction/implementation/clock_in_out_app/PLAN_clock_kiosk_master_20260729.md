## Goal and intent

- Goal: build the fourth application of the monorepo — an always-on **shop-floor kiosk** running on a shared device (wall tablet / terminal / floor PC) where workers clock in/out of their shift with a personal **4-digit code** (or their working email). Declared states (lunch, cleaning, meeting…) are wrapped at the domain layer for future pages but have **no v1 UI** (decision #10). Composed of:
  1. `@beyo/worker-shifts` (`packages/worker-shifts`) — the shift **domain package**: types, query keys, API functions, query hooks, action hooks, roster matching. No UI. Reusable tomorrow by the workers/managers apps.
  2. `@beyo/clock-kiosk` (`packages/clock-kiosk`) — the kiosk **feature package**: the whole kiosk experience (keypad → identity confirm → action → result), its flow state machine, all screens/components, surface exports. The kiosk must be mountable as a page in any host app.
  3. `apps/floor-app/ManagerBeyo-app-floor` — a **thin shell** app: floor-scope auth, device configuration, kiosk chrome, providers, styling registration. Owns zero kiosk logic.
  4. Floor-scope **device auth** support in `@beyo/api-client` + `@beyo/auth` (non-expiring persisted token, no refresh).
- Business/user intent: workers walk up, type a code, see themselves confirmed (photo + name), tap one button, and walk away — one hand, gloves on, a few seconds per person. Managers get truthful shift machinery feeding the existing worker-stats surfaces.
- Non-goals (v1):
  - **Declared-states UI** (user decision 2026-07-29): the kiosk ships clock in/out only. The domain wrappers exist in `@beyo/worker-shifts` (Phase 1) because the package serves future pages, but no kiosk screen consumes them — Phase 5 is shelved.
  - Backend changes of any kind (gaps are documented in `BACKEND_REQUIREMENTS_clock_kiosk_20260729.md`, not implemented).
  - Managing `clock_in_code` assignment (backend phase 6; a managers-app feature later — not this capability).
  - The legacy `POST /worker-shifts/clock` toggle route (explicit routes only, per handoff §5).
  - Push notifications, Connecteam anything, payroll exports.
  - Editing the design images/readme or the backend handoff.

| 1 | Naming | App `apps/floor-app/ManagerBeyo-app-floor`, package name `managerbeyo-app-floor`, dev port **5175**. Packages `@beyo/worker-shifts`, `@beyo/clock-kiosk`. |
| 2 | Shell shape + the **`rise` surface** (amended by user 2026-07-29) | **No bottom tabs, no TabSlideStack, no SlideStack.** The app copies the presentation-studio minimal `src/app/` (providers, router, RootRoute, surface-registry) and keeps the surface registry + `SurfaceProvider` engine — but this app does **not** use the existing surface types. The rise surface is used **everywhere** in the kiosk: the flow screens themselves (identity confirm, result/summary) open as rise surfaces over the **always-mounted keypad page**, and overlay surfaces (device settings) use it too. Closing any surface — done, back, timeout — fades down and reveals the keypad beneath, which makes the "terminal never rests on a personal screen" rule structural. |
| 3 | Auth persistence | Floor scope stores its non-expiring token in `localStorage` (device storage), per handoff §2. `401` anywhere ⇒ token revoked ⇒ clear + return to device sign-in. | 5 | Identification | Client-side roster matching per handoff §3: `GET /users?role=worker&compact=true&limit=200` cached via TanStack Query (`refetchInterval` 2 min + refetch on focus), trim input, code exact, email case-insensitive. ## Division of labor — Claude (design/components) vs. Codex (logic/assembly)

Same seam as the presentation capability (proven): presentational components are props/context-only; logic lives in hooks/stores/controllers/pure modules.

- **Claude owns component files** — DOM structure, Tailwind classes, kiosk tokens, motion, skeletons. For every UI phase Claude builds the phase's **component kit first**, props-first against mock data, matching `design_readme.md`'s visual system, before the Codex session starts. Each component ships with a typed prop contract (data in, callbacks out) and `data-testid`s.
- **Codex owns everything else** — types, api, hooks, stores, controllers, matching, mapping, persistence, tests — and the **assembly**: composing Claude's components into pages and feeding controller state through their props.
- **Codex treats Claude's components as read-only.** A prop-contract misfit is recorded in the child plan's Review log; purely additive optional props may be added without touching DOM/classes; anything structural or visual waits for Claude. Codex never restyles, never restructures markup, never edits class lists.
- Interaction-heavy components (keypad keys, code cells, shake animation, carousel, auto-return countdown) expose **injected callbacks only** (`onDigit`, `onDelete`, `onSubmit`, `onExpire`…); timers and matching live in the store/controller, not in components.

## Risks and mitigations

- Risk: floor-scope changes to `@beyo/api-client`/`@beyo/auth` regress the three live apps.
  Mitigation: Phase 2 is logic-only, gated on the existing auth test suites + full root typecheck; the persisted path is strictly `app_scope === "floor"`-conditional; review prompt orders a diff-level check of the non-floor code paths.
- Risk: backend phases land with contract drift against the handoff.
  Mitigation: the handoff is edit-first authority; mocks are keyed to its shapes; Phase 7 re-runs flows against any endpoint that has flipped ✅ before removing its mock.
- Risk: shared-device token in localStorage is readable by anyone at the terminal.
  Mitigation: accepted by the backend contract (device is the trust anchor; the code identifies, never authenticates); logout is permanent revocation; no other scope ever persists.
- Risk: auto-return timers + async actions race (action resolves after return-to-keypad).
  Mitigation: the flow store owns a session id per kiosk interaction; stale async results against a different session id are dropped; unit tests cover the race in Phase 4.
- Risk: 200-worker roster cap (`limit=200`) silently truncates larger workspaces.
  Mitigation: surfaced in `BACKEND_REQUIREMENTS` (pagination or raised cap); v1 logs a console warning when `users.length === 200`.
- Risk: the declare flow has no design ground truth. — **Closed**: declares removed from v1 (decision #10, user 2026-07-29); the risk transfers to the future declare-pages capability.
- Risk: the new `rise` surface type destabilizes the shared SurfaceProvider engine used by three live apps.
  Mitigation: the type is registered additively (new shell component + renderer case); existing surface-type code paths untouched; `@beyo/ui` surface tests extended in Phase 3 and the reviewer diff-audits the renderer change.
