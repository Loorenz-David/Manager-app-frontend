Event
Event name	email_batch:delivery_completed
Delivery	Sent only to the requesting user's room (user:{requested_by_user_id}) — not workspace-broadcast
When	After the background send job finishes its delivery attempt and commits
Payload

{
  "client_id": "01J...ULID",          // the background job's task_client_id (the entity id)
  "request_kind": "coordination_batch", // or "batch_send"
  "connection_client_id": "01J...",     // email connection used to send
  "attempted_count": 5,                 // messages actually attempted this run
  "sent_count": 4,                      // succeeded
  "failed_count": 1,                    // failed
  "message_ids": ["01J...", "01J..."]   // EmailMessage client_ids in this batch
}
Field notes for the frontend
client_id — this is the job/task id, injected automatically by the socket handler (every event carries a top-level client_id). It is not a message or task id you'd navigate to. Treat it as the batch/job identifier.
request_kind — "coordination_batch" (from the customer-coordination email batch route) or "batch_send" (generic batch). Use this to decide which UI surface reacts.
sent_count / failed_count — drive the toast: e.g. all-success vs. partial-failure vs. all-failed. attempted_count == sent_count + failed_count.
message_ids — the specific EmailMessage client_ids, if you want to refetch/mark those threads.
Important caveats
No per-message detail — this is an aggregate summary. Which specific message failed is not in the payload (it's in email_message.send_error in the DB). If the UI needs to show which one failed, that's a follow-up (either expand the payload or refetch by message_ids).
Coordination state does not change on failure — a failed send still leaves the task in coordinating. Don't infer a state rollback from failed_count > 0.
Retries can emit a second event — if the job partially fails and retries the still-pending subset, a second email_batch:delivery_completed may arrive describing that subset. Make the handler idempotent/additive rather than assuming exactly one event per batch.
This is still a plan, not merged — the event name and shape are proposed. If the frontend wants a different name or an extra field (e.g. workspace_id, or a task_ids list for coordination batches), tell me now and I'll adjust the plan before it's implemented.
