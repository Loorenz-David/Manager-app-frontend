BACKEND:

We will now develop the shopify integration capability for creating or updating a product in shopify, using the already stablish shopify system.

The goal is to allow a user to create or update a product in one or multiple shopify shops. Shops which the current user workspace has integration with.

find_shopify_products:
this  service we will create is a find product on given shopify shop, this service will use GrapQL . the user can pass an article_number or sku . The service should find a product matching exactly the article_number or sku given ( article_number is barcode in shopify semantics ).
This service will return the product id if found, if none it will return a flag that let's other services using this service understand there is no product with those identity fields.
This query is barcode or sku it doesn't have to be "and" . at least one must be provided, otherwise it raises an error.


create_shopify_products:
This service will allow the user to pass a payload which will be used for creating a product in shopify, after the creation it will return the product id that was created by shopify ( other info might be added on the return shape ).
This service should allow batch creation of items from day one thus the plural naming of the service.
This service will have a layer where it will be able to fill up defaults if missing, this should be scalable and easy to maintain, so far the only default is status: draft

update_shopify_products:
This service will allow the user to pass a payload which will be used for updating a product in shopify, after the update only the confirmation or error is return.
This service should allow batch update of items from day one thus the plural naming of the service.

paylaod builders and normalizers:
we will need to create payload builders and normalizers for using this create and update shopify products, as those services will only accept build and normalized payloads for executing their request.


create_or_update_shopify_products:
This service will be a light orchestrator which will take target items with already build and normalized payloads. It will use the find_shopify_products to determine the services it should use for each target item, 
either update_shopify_products or create_shopify_products .  This orchestrator should be efficient and optimal by handling the batch capability this services provide. when calling create and update at the same time it should use async jobs for speed.
Before the transaction begins it will generate the db instances for each item ( efficently ), on the item shopify event table, this will allow the frontend to track the event status as this serivice will be used as with a background worker.
After the operations this service should update the item shopify event status instance with the result of the transaction and comunicate a socket event with the client id of the items it suceeded with and a fail list also. 


process_items_in_shopify:
This service will be the service used by the current app routers ( routers that will be created bellow ), this service will use the payload builders and normalizers to build the payloads for then sending them through create_or_update_shopify_products
Because this process can take time while query and either creation or update. we will make this service to delegate the create_or_update_shopify_products to a worker, there is already a shopify worker dedicated for shopify transactions.


router_process_itemes_in_shopify:
This router will user the service process_items_in_shopify as it's run function . and will map the incooming payload schema the frontend can send.


The frontend will send to this router a list of objects for either creating or updating a product on shopify using the system we just described.
The user should be able to send: product images ( for uploading, im not sure how this upload image system works ), product metafields, product category, product price, product description, product title, product status, product weight ( for shipping fields in shopify ), product tags, sku, item_article_number ( barcode ) .
The metafields key will have an object as value, each key representing the metafield name and the value as the metafield value that should be store ( the frontend will be strict about the metafield keys so the backend doesn't need to care about that ).
